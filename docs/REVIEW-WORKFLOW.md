# レビュー運用ルール（LINE .NET クライアント）

## 方針

- **4 つのレビュアー役**を、各作業段階の**ゲート**として設ける。合格するまで次段階に進まない。
- 各レビュアーは**サブエージェント**として独立コンテキストで自動実行し、結果を集約して報告する。
- **最終的な go / no-go 判断は人（小林さん）**が行う。レビュアーは合否判定と指摘を出すが、次工程への通過を確定するのは人。
- 生成コード本体は行単位レビューの対象外（Kiota は可読性が非目標）。レビュー主眼は**手書きコード**と**公開 API の使い勝手**。

## レビュアー役と担当

各役は **プロジェクト固有のサブエージェント**（`.claude/agents/*.md`、リポジトリ管理）として実行する。深掘りが必要なときはビルトインスキル（`code-review` / `security-review`）を併用する。

| 役 | 主な観点 | サブエージェント / 併用スキル |
|---|---|---|
| 仕様レビュアー | OpenAPI 妥当性、Kiota 検証警告（DivergentResponseSchema / GetWithBody / InconsistentTypeFormat）、base URL / server 定義（R1）、命名品質（R2） | `spec-reviewer` |
| コードレビュアー | 手書きグルー（認証・DI・ファサード・Webhook 署名）、公開 API の使い勝手、エラーハンドリング | `code-reviewer`（＋ビルトイン `/code-review`） |
| セキュリティレビュアー | トークン保持/送出、`AllowedHostsValidator`、Webhook 署名（HMAC-SHA256）、シークレット管理 | `security-reviewer`（＋ビルトイン `/security-review`） |
| テスト・アーキ観点 | 設計判断（ADR）の妥当性、テスト観点/カバレッジの充足 | `test-arch-reviewer` |

## ゲート定義

各ゲートで担当レビュアーが `PASS` / `CONCERNS` / `FAIL` と具体的指摘を返す → 集約報告 → 人が通過可否を決定。

| ゲート | タイミング | 担当レビュアー | 通過基準（例） |
|---|---|---|---|
| **G0 設計** | 設計方針ドキュメント確定時 | テスト・アーキ観点 | 設計判断に致命的な穴がない／R1 の検証計画がある |
| **G1 仕様** | 仕様スナップショット取得後・生成前 | 仕様レビュアー | 生成を妨げる検証エラーがない／ホスト・命名リスクを把握 |
| **G2 生成/PoC** | Messaging API の PoC 生成後 | コード＋テスト・アーキ観点 | 公開 API が実用的／R1・R2 の実挙動を確認 |
| **G3 手書き実装** | 認証・DI・Webhook 署名の実装後 | コード＋セキュリティ | 認証/署名が正しく安全／DI が妥当 |
| **G4 リリース前** | パッケージ化直前 | 全 4 役 | 破壊的変更の把握／テスト充足／セキュリティ懸念解消 |

## 記録

各ゲートのレビュー結果（判定・指摘・対応）は `docs/reviews/` に日付付きで残し、追跡可能にする。

## CI 連携（将来）

今回はサブエージェント運用を主とし、CI（GitHub Actions）連携は後続で検討（Kiota 検証・ビルド・テスト・差分チェックの自動化）。
